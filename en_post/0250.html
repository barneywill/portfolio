Linux server upgrade glibc failure recovery

📅 January 24, 2019
📖 1 min read
👁️ 6078 views

Redhat6 system installs glibc-2.12 by default. Some software depends on glibc-2.14. In this case, you need to upgrade glibc. Download and install http://ftp.gnu.org/gnu/glibc/glibc-2.14.tar.gz

# ./configure --prefix=/usr --disable-profile --enable-add-ons --with-headers=/usr/include --with-binutils=/usr/bin
# make
# make install

As a result, make install reports an error. At the same time, all commands except cd cannot be used. Various shared libraries will be reported: *: cannot open shared object file: No such file or directory.

ls: error while loading shared libraries: libselinux.so.1: cannot open shared object file: No such file or directory

These shared libraries are located under /lib64/, and the machine cannot log in remotely at this time.
Now there is only one terminal root account logged in to the server, and nothing can be done except executing cd, omg
All kinds of Google can't solve it, so you have to work hard on your own.

1 First try to remotely transfer all files and links under /lib64/ from other servers to the local machine, but various transfer commands cannot be used, such as nc, scp, etc.

2 Secondly, I suspect that the link may be damaged and try to manually rebuild the link that reported the error.

# ln - s libtinfo.so.5.7 libtinfo.so.5
ln: creating symbolic link `libtinfo.so.5': File exists

Although ls cannot be used, it seems that various files and links under /lib64/ are still there, so why does it report No such file or directory?

3 Check the current environment variables through export again (export can still be used):

# export
declare - x LD_LIBRARY_PATH="/usr/local/lib"

Try to modify LD_LIBRARY_PATH and add /lib64:

export LD_LIBRARY_PATH=/lib64:$LD_LIBRARY_PATH

Many commands can be used. The process of upgrading glibc this time is as follows. Take one of the libraries as an example:

Before installation:

-rwxr-xr-x 1 root root 161776 Jun 19 2018 ld-2.12.so
lrwxrwxrwx 1 root root 10 Jun 19 2018 ld-linux-x86-64.so.2 - > ld-2.12.so

After installation:

-rwxr-xr-x 1 root root 161776 Jun 19 2018 ld-2.12.so
-rwxr-xr-x 1 root root 838308 Jan 24 15:41 ld-2.14.so
lrwxrwxrwx 1 root root 10 Jan 24 16:28 ld-linux-x86-64.so.2 - > ld-2.14.so

Roll back the changes in this installation, that is, change all links to point back to version 2.12

# ls - l /lib64|grep 2.14|grep lrw|awk '{print "ln - snf "$11" "$9}'|sed 's/2.14/2.12/g'
ln - snf ld-2.12.so ld-linux-x86-64.so.2
ln - snf libBrokenLocale-2.12.so libBrokenLocale.so.1
ln - snf libanl-2.12.so libanl.so.1
ln - snf libc-2.12.so libc.so.6
ln - snf libcidn-2.12.so libcidn.so.1
ln - snf libcrypt-2.12.so libcrypt.so.1
ln - snf libdl-2.12.so libdl.so.2
ln - snf libm-2.12.so libm.so.6
ln - snf libnsl-2.12.so libnsl.so.1
ln - snf libnss_compat-2.12.so libnss_compat.so.2
ln - snf libnss_dns-2.12.so libnss_dns.so.2
ln - snf libnss_files-2.12.so libnss_files.so.2
ln - snf libnss_hesiod-2.12.so libnss_hesiod.so.2
ln - snf libnss_nis-2.12.so libnss_nis.so.2
ln - snf libnss_nisplus-2.12.so libnss_nisplus.so.2
ln - snf libpthread-2.12.so libpthread.so.0
ln - snf libresolv-2.12.so libresolv.so.2
ln - snf librt-2.12.so librt.so.1
ln - snf libutil-2.12.so libutil.so.1

Execute them all once, the fault will be restored, various commands can be used, and the machine will resume remote login.
