2. Design plan

Split the data into: historical data (HDFS+Parquet+snappy) + recent data (Kudu), which can have various advantages:

  • 1) Overall disk usage is less than 10%;
  • 2) Less time-consuming query;
  • 3) Recent data is updated in real time;
  • 4) Recent data can be modified;
  • 5) The Kudu cluster restart time is reduced by 90%;
  • 6) Impala parallel scan: scan Kudu + scan HDFS;

 

Three transformation plans

Take advantage of views

create view v_table as
select * from parquet_table where dt < 'seven days ago'
union all
select * from kudu_table where dt >= 'seven days ago';

The client can replace kudu_table with v_table;

 

Four others

Kudu question:

  • The Kudu client version used by Flume Kudu sink is too low and has bugs. The token will not be automatically refreshed and an error will be reported after 7 days because the token is invalid. The bug can be solved after upgrading Kudu client, but the guava library version used by Kudu client and Flume is conflicting;
  • After partitioning by dt, the number of tablets is too large, the disk space is too large, and the memory is too much;
  • Because of the large number of tablets and large disk space, it takes 10-20 minutes to initialize each time the Kudu cluster is restarted;
  • When Kudu takes up too much memory, it will refuse write operations;
  • Using Kudu as a single data warehouse supports writing and querying at the same time, which can easily affect each other. A large number of writes will affect queries, and a large number of queries will affect writes, which will lead to data loss or slow query;
  • Kudu supports updates. All data can be deleted with a delete or drop, which is more dangerous as a single data warehouse;
