How to achieve "efficiency" when processing large batches of data while also implementing the "breakpoint resume" function

📅 October 20, 2018
📖 1 min read
👁️ 1443 views

question

There is a task of sending 1 million text messages. How to shorten the sending time as much as possible, and at the same time, if the task hangs up due to various reasons, for example, the task hangs up after sending 500 thousand text messages, and only the remaining 500 thousand text messages will be sent after restarting the task?

 

This is a relatively common question, and the easy way to think of it is:

Option 1

step

  1. Use a database to store all data (such as 1 million text messages to be sent), and set the status, unprocessed is 0, processed is 1;
  2. When the task is executed, all data with status=0 are queried, that is, the data to be processed;
    1. 　　Process each item one by one, and set status=1 after processing to avoid repeated processing;

analyze

This solves the problem, but there are someshortcoming：

  • a The efficiency of serial processing of data is very low;
  • b The data must be stored in an updateable storage, such as a database. Non-updateable storage such as Hive and files is not supported;
  • c Traditional RDBMS has limited support for data volume;
  • d Even if it is serialized, in extreme cases there may still be a piece of data that is processed repeatedly (repeatedly sending text messages);

Disadvantage d is that the sending operation and updating the database status are separate, and the sending operation cannot be rolled back, so it cannot be fundamentally solved through distributed transactions. This problem is basicallyNo solution, that is, there is always the possibility of repeated processing,We can only try to reduce the probability of repeated sending。

 

Since disadvantage d cannot be avoided, disadvantage a can be solved through multi-threading + batch submission of transactions:

Option 2

step

  1. Same as above
  2. Same as above
    1. 　　Each time B pieces of data are read, the data is evenly distributed to C threads for simultaneous processing. After each thread processes D pieces of data, the status=1 of these D pieces of data is set in batches;

(For example, each time 1000 text messages with status=0 are read, they are distributed to 10 threads for sending at the same time. Each thread sends 100 text messages, and each thread updates the status=1 of these 20 text messages in batches after successfully sending 20 text messages.)

analyze

Option 2 vs. Option 1

Theoretically, the time can be shortened to less than 1/C (1/10 in the above example). At the same time, in the most pessimistic case, C*D data (10*20=200 in the above example) may be processed repeatedly, that is, when shortcoming a is solved, shortcoming d is amplified, while shortcomings b and c still exist;

 

Is it possible to solve shortcomings a, b, and c at the same time?

Option three

step

  1. The data to be processed is stored in a database, Hive, or file;
  2. Before processing, first query the offset of the last processing of the current task (if it is a database or Hive, offset is the auto-incremented ID or uuid; if it is a file, offset is the number of rows), if it does not exist, set offset=0, and the offset can be stored in the database;
  3. Continue to query the data to be processed starting from the last processed offset; (the database or Hive is a sorting query that skips the previous rows, and the file directly skips the previous rows according to the number of rows)
    1. 　　Each time B data is queried, it is distributed to C threads for processing. When all B data are processed, offset+=B is set;

 

analyze

Option 3 compared to Option 2

Disadvantage a: It saves more than 99% of database operations and increases efficiency by N times;
Disadvantages b and c are perfectly solved;
In terms of disadvantage d, option three has at most B data repeated processing (1000 in the above example), and option two has at most C*D data repeated processing (10*20=200 in the above example). That is, option three magnifies disadvantage d compared to option two;

 

Is it possible to further optimize disadvantage d?

Option 4

step

  1. Same as above
  2. Same as above
  3. Same as above
    1. 　　Each time B data is queried, it is distributed to C threads for processing. Each thread maintains a currently processed relative_offset in the cache (memcache or Redis, you can also put it in the database). If relative_offset!=0, the first relative_offset data is skipped; after all threads are processed, set relative_offset=0 for all threads, and set offset+=B at the same time;

(For example, each time 1000 unsent text messages are queried, they are distributed to 10 threads for processing. Each thread maintains a relative_offset in the cache. The initial value is 0. Each time a message is sent, the relative_offset+=1 in the cache of the thread is set. After 10 threads are processed, the relative_offset=0 of all threads is set, and offset+=1000 is set.)

Problem playback

After sending 8000 text messages, the next 1000 text messages to be sent are taken out, that is, 8001-9000. At this time, they are divided into 10 threads. The first thread distributes the text messages 8001-8100, the second thread distributes the text messages 8101-8200,..., and the 10th thread distributes the text messages. The text message is 8901-9000. After sending for a period of time, the relative_offset of the first thread is 49, the relative_offset of the second thread is 31, and other threads are arbitrary. At this time, the process hangs. After the task is restarted, the offset is obtained. t=8000, this time take out the next 1000 text messages to be sent, and still distribute them to 10 threads. The first thread distributes text messages 8001-8100, the second thread distributes text messages 8101-8200,..., and the 10th thread distributes text messages 8901-9000. , the first thread finds that relative_offset=49, then continues to send text messages of 8050-8100, the second thread finds that relative_offset=31, then continues to send text messages of 8132-8200, and so on for other threads.

analyze

Option 4 compared to Option 3

In terms of disadvantage d, in the most pessimistic case, both options three and four will have B pieces of data sent repeatedly, but the probability of the occurrence of option four is extremely low (it will only happen if all threads hang up between setting relative_offset=0 and setting offset+=1000), and with a very high probability, only C pieces of data will be sent repeatedly. This is much better than the C*D effect of option two;

 

To sum up, Solution 4 can simultaneously achieve "efficiency" and "breakpoint resume", and it is a relatively general solution that can implement a set of base classes. Reading the data to be processed and processing a single piece of data are implemented as template methods by subclasses, and can be quickly applied to all problem scenarios.
