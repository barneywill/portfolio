Kylin frequent OOM problem

📅 December 13, 2018
📖 2 min read
👁️ 946 views

A kylin cluster in the company will exit OOM one by one every Tuesday afternoon, very regularly. The kylin cluster has 5 nodes, and the memory allocated to each node has been continuously increased to more than 70G, but the problem remains the same;


After investigation, it was found that the number of requests for the kylin cluster does increase every Tuesday afternoon. It may be a bug in kylin, or it may be due to other reasons. When the memory usage of the node kylin process increases, printing the thread stack shows that many threads are stuck, synchronized, and various managers, such as CubeManager, DictionaryManager, MetadataManager, and Metadata. Taking taManager as an example, looking at the kylin code, we found that these Managers have similar routines, including clearCache and getInstance (synchronized). Then Constructor will be called in getInstance, and a bunch of things will be loaded in Constructor. This loading process is relatively slow, so getInstance will be synchronized for a long time:


org.apache.kylin.metadata.MetadataManager

    public static void clearCache() {
        CACHE.clear();
    }
    
    public static MetadataManager getInstance(KylinConfig config) {
        MetadataManager r = CACHE.get(config);
        if (r != null) {
            return r;
        }

        synchronized (MetadataManager.class) {
            r = CACHE.get(config);
            if (r != null) {
                return r;
            }
            try {
                r = new MetadataManager(config);
                CACHE.put(config, r);
                if (CACHE.size() > 1) {
                    logger.warn("More than one singleton exist");
                }

                return r;
            } catch (IOException e) {
                throw new IllegalStateException("Failed to init MetadataManager from " + config, e);
            }
        }
    }

    private MetadataManager(KylinConfig config) throws IOException {
        init(config);
    }

    private void init(KylinConfig config) throws IOException {
        this.config = config;
        this.srcTableMap = new CaseInsensitiveStringCache<>(config, "table");
        this.srcTableExdMap = new CaseInsensitiveStringCache<>(config, "table_ext");
        this.dataModelDescMap = new CaseInsensitiveStringCache<>(config, "data_model");
        this.extFilterMap = new CaseInsensitiveStringCache<>(config, "external_filter");

        reloadAllSourceTable();
        reloadAllTableExt();
        reloadAllDataModel();
        reloadAllExternalFilter();

        // touch lower level metadata before registering my listener
        Broadcaster.getInstance(config).registerListener(new SrcTableSyncListener(), "table");
        Broadcaster.getInstance(config).registerListener(new SrcTableExtSyncListener(), "table_ext");
        Broadcaster.getInstance(config).registerListener(new DataModelSyncListener(), "data_model");
        Broadcaster.getInstance(config).registerListener(new ExtFilterSyncListener(), "external_filter");
    }

 

After checking the codes of various versions of kylin, I found that they all use this routine. It seems that kylin does not think this is a problem. This will indeed lead to some potential problems. For example, when the load is high, there will be a sudden refresh, and a large number of requests will be synchronized. Will this cause OOM?


Further inspection of the thread stack revealed that the tomcat thread pool was almost full at that time. This is also easy to understand. The previous requests were synchronized, and new requests continued to come in, and then the thread pool was full. It suddenly occurred to me that once synchronized ended, all requests began to be processed at the same time, and some of the requests may occupy more memory, so the memory may instantly It’s unbearable. This is an avalanche effect. The above scenario is actually similar to the stress test scenario, that is, the server is running at full load and all threads in the thread pool are processing requests. If the number of thread pools configured in tomcat is too large, the server will not be able to support it. This is the reason for OOM. If you do not change this configuration, no matter how large the memory configuration is, OOM will still occur. Just make the tomcat thread pool configuration smaller;

 

Another method is to add control to the Load Balancer. Once the response is slow, mark it as unhealthy and distribute the requests to other nodes. This way, a large number of requests will not accumulate on the synchronized nodes and problems can be avoided;
