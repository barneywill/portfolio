Hive executes multiple inserts at the same time and only one of the overwrite tables can be executed.

📅 December 27, 2018
📖 5 min read
👁️ 10207 views

hive 2.1

1 question

Recently, there was a scenario where data was written to multiple partitions of a table. In order to shorten the execution time, a concurrent method was used. Multiple SQLs were executed at the same time, writing different partitions respectively, and enabling dynamic partitioning at the same time:

set hive.exec.dynamic.partition=true

insert overwrite table test_table partition(dt) select * from test_table_another where dt = 1;

It turns out that only one SQL is running, and other SQL will be stuck;
Check the Hive thrift server thread stack and find that the requests are stuck on DbTxnManager. The key configuration of Hive is as follows:

hive.support.concurrency=true
hive.txn.manager=org.apache.hadoop.hive.ql.lockmgr.DbTxnManager

Configure the corresponding default values ​​and comments:

org.apache.hadoop.hive.conf.HiveConf

    HIVE_SUPPORT_CONCURRENCY("hive.support.concurrency", false,
        "Whether Hive supports concurrency control or not. \n" +
        "A ZooKeeper instance must be up and running when using zookeeper Hive lock manager "),

    HIVE_TXN_MANAGER("hive.txn.manager",
        "org.apache.hadoop.hive.ql.lockmgr.DummyTxnManager",
        "Set to org.apache.hadoop.hive.ql.lockmgr.DbTxnManager as part of turning on Hive\n" +
        "transactions, which also requires appropriate settings for hive.compactor.initiator.on,\n" +
        "hive.compactor.worker.threads, hive.support.concurrency (true), hive.enforce.bucketing\n" +
        "(true), and hive.exec.dynamic.partition.mode (nonstrict).\n" +
        "The default DummyTxnManager replicates pre-Hive-0.13 behavior and provides\n" +
        "no transactions."),

runInternal will call requiresLock to determine whether a lock is required. requiresLock has two judgments:

  • Call checkConcurrency, checkConcurrency will check Hive.support.concurrency=true to require lock;
  • Call Task.requireLock, only some tasks require lock;

If it is determined that a lock is needed, acquireLocksAndOpenTxn will be called, and acquireLocksAndOpenTxn will call HiveTxnManager.acquireLocks to obtain the lock;

It can be seen that when dynamic partitioning is enabled, the lock granularity is DbName+TableName, which will result in multiple SQL only one SQL can get the lock, and other SQL can only wait;

Three Summary

There are several ways to solve the problem:

  1. Turn off dynamic partitioning: set Hive.exec.dynamic.partition=false
  2. Turn off concurrency: set Hive.support.concurrency=false
  3. Close the transaction: set Hive.txn.manager=org.apache.hadoop.Hive.ql.lockmgr.DummyTxnManager

Choose one of the three, and the first one is recommended because in the scenario just now, dynamic partitioning is not needed;
