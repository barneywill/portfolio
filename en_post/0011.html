1. Hot/Warm/Cold Tiering

Index Lifecycle Management Policy

Index features

  • Hot: The index is updated and a large number of queries are made
  • Warm: The index is not updated and is occasionally queried
  • Cold: The index is not updated and is rarely queried.
  • Delete: The index is not updated and is not queried

Reference:https://www.elastic.co/guide/en/elasticsearch/reference/7.0/index-lifecycle-management.html

According to the index characteristics, the Elasticsearch cluster can be divided into several small clusters:

  • Hot cluster: stores Hot indexes
  • Warm cluster: stores Warm indexes
  • Cold cluster: stores Cold indexes (optional)

https://www.elastic.co/blog/implementing-hot-warm-cold-in-elasticsearch-with-index-lifecycle-management

The simplest approach is to manage the cluster with Hot and Warm tiers. Their characteristics are:

  • Hot cluster: multiple CPUs, large memory, small hard disk, small Shard, and handles a large number of read and write requests concurrently
  • Warm cluster: less CPU, small memory, large hard disk, large Shard, and handles a smaller number of read and write requests

When an index is moved from a Hot cluster to a Warm cluster, it is usually necessary to change the small shard into a large shard. Here a shrink operation is required, that is, multiple shards of an index are merged into fewer shards. For example, five 10G shards are merged into one 50G shard. The shrunken index can be searched through the original index alias.

https://www.elastic.co/guide/en/elasticsearch/reference/7.0/indices-shrink-index.html

2. Memory Allocation

The node memory of Elasticsearch is divided into 2 parts:

  • JVM memory
  • Lucene index memory: mainly affected by disk size and shard size

The maximum memory occupied by the second Lucene index can be estimated by the disk size. Most of the remaining memory can be allocated to the JVM. For example, the current node has 32G of memory, the disk occupies 50%, and Lucene uses 1G of memory. It can be estimated that Lucene will use up to 2G of memory when the disk is full. Then most of the remaining 30G, such as 28G, can be allocated to the JVM for use, which can optimize the memory usage of the node.

3 Uneven disk usage among different nodes

Elasticsearch's cluster balancing strategy is to ensure that the number of shards between different nodes is approximately equal. If the sizes of different shards are very different, uneven disk usage of different nodes will occur. This can be divided into two types:

Hot node disk usage is uneven

Adjust the ILM strategy and change the index rolling strategy on the hot node to use size instead of time. This can reduce the unequal size of shards on the index hot node and further reduce the possibility of uneven disk distribution.

Warm node disk usage is uneven

You can regularly delete empty indexes, merge small indexes and other operations to reduce the number of shards and further reduce the possibility of uneven disk distribution.

4. Other Notes

Disk usage percentage

Hot nodes and hot node disks must be expanded in time when 90% is used.

Performance Bottlenecks

Pay attention to the fact that nodes in the cluster have their own performance bottlenecks and processing capabilities, such as

  • max_restore_bytes_per_sec: must be lower than the disk limit, otherwise it will easily cause the node to die.

  • cluster_concurrent_rebalance and node_concurrent_recoveries: If the Warm node is occasionally kicked off by the master, it may be because the shrink or migration concurrency is too large and exceeds the cluster's capacity. In this case, it is best to lower these two concurrency limits.
