The reason for the error is described clearly in the message. The standalone mode directly uses the local disk, and the local disk does not support hsync. Check the configuration:

  <property>

    <name>hbase.procedure.store.wal.use.hsync</name>

    <value>true</value>

  </property>

Change it to false and restart, but the error is still reported. Follow up the code:

org.apache.hadoop.hbase.procedure2.store.wal.WALProcedureStore

    this.enforceStreamCapability = conf.getBoolean(CommonFSUtils.UNSAFE_STREAM_CAPABILITY_ENFORCE, true);

    final String durability = useHsync ? "hsync" : "hflush";
    if (enforceStreamCapability && !(CommonFSUtils.hasCapability(newStream, durability))) {
        throw new IllegalStateException("The procedure WAL relies on the ability to " + durability +

...

It can be seen that if HBase.procedure.store.wal.use.hsync is true, hsync is used; if it is false, hflush is used;
Both will report errors. At this time, I noticed that there is another variable controlling enforceStreamCapability. The corresponding configuration of this variable is HBase.unsafe.stream.capability.enforce. Set the configuration to false and the problem is solved;

When standalone HBase is needed, it is usually used by beginners for practice, but there are also some products in use, such as Ambari's metrics collector;

About Standalone HBase

This is the default mode. In standalone mode, HBase does not use HDFS -- it uses the local filesystem instead -- and it runs all HBase daemons and a local ZooKeeper all up in the same JVM. Zookeeper binds to a well known port so clients may talk to HBase.

For details on the standalone method, please refer to the official documentation:
http://hbase.apache.org/0.94/book/quickstart.html
