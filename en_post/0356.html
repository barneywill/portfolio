1 Introduction

1 official website

https://azkaban.github.io/

Azkaban was implemented at LinkedIn to solve the problem of Hadoop job dependencies. We had jobs that needed to run in order, from ETL jobs to data analytics products.

Initially a single server solution, with the increased number of Hadoop users over the years, Azkaban has evolved to be a more robust solution.

Azkaban was developed by LinkedIn to solve the task dependency problem in the Hadoop environment. The LinkedIn team has many tasks that need to be run in sequence, including ETL tasks and data analysis tasks;

Azkaban started as a single-server solution, but now it has evolved into a more robust solution; (unfortunately, the current version of WebServer is still a single-point solution)

Azkaban consists of 3 key components:

  • Relational Database (MySQL)
  • AzkabanWebServer
  • AzkabanExecutorServer

Azkaban has three core components: MySQL, WebServer, and ExecutorServer;

2 Deployment

 

3 Database table structure

 

projects: projects

project_flows: workflow definition

execution_flows: workflow instance

execution_jobs: task instance

triggers: scheduling definition

ps: Many data in the table are encoded, enc_type is the encoding type (the corresponding enumeration is EncodingType), 2 is gzip encoding, others are unencoded, 2 needs to call GZIPUtils.transformBytesToObject to parse to get the original string;

4 concepts

l Job: the smallest execution unit, as a node of DAG, that isTask

l Flow: It consists of multiple jobs, and the dependency attributes of the jobs are configured through dependent, that is,Workflow

l Tirgger: Trigger Flow based on specified Cron information, that isScheduling
