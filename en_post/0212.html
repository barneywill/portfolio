Third-party open source solution ASFC

For the scheduler single point problem, there is a third-party solution: https://github.com/teamclairvoyant/airflow-scheduler-failover-controller

 

The Airflow Scheduler Failover Controller (ASFC) is a mechanism that ensures that only one Scheduler instance is running in an Airflow Cluster at a time. This way you don't come across the issues we described in the "Motivation" section above.

You will first need to startup the ASFC on each of the instances you want the scheduler to be running on. When you start up multiple instances of the ASFC one of them takes on the Active state and the other takes on a Standby state. There is a heart beat mechanism setup to track if the Active ASFC is still active. If the Active ASFC misses multiple heart beats, the Standby ASFC becomes active.

The Active ASFC will poll every 10 seconds to see if the scheduler is running on the desired node. If it is not, the ASFC will try to restart the daemon. If the scheduler daemons still doesn't startup, the daemon is started on another node in the cluster.

 

Airflow Scheduler Failover Controller (ASFC) is implemented as follows: only one of multiple instances is in the active state. The instance in the active state will check whether the scheduler process is alive every 10 seconds and restart the process as needed;

The bad news is that this solution is not compatible with the new version of airflow 1.10

2. Research on airflow production environment deployment plan based on mesos+HDFS

Same part

consistent with official

  • Use MySQL database as metabase

Inconsistent with the official 1

  • All modifications to the dags directory are synchronized to HDFS to ensure the high availability of the dags directory.
  • Use HDFS NFSGateway to mount HDFS on all possible scheduler nodes. No matter which node the scheduler is deployed on, use the same dags directory.
  • Use Nginx+marathon-lb to expose airflow's webserver to the outside world, and you can operate the process or view the execution of the process, etc.

1 airflow single instance container deployment solution

Inconsistent with official 2

  • The webserver, scheduler, and worker run as Docker containers, and only one instance is deployed on multiple nodes. Marathon ensures availability, and marathon-lb does service discovery.
  • Workers use LocalExecutor, that is, all tasks are executed using child processes.
    • In order to enable the LocalExecutor of the worker in the container to access external cluster functions, a feasible way is to mount the parent directories of various components into the container (for example, each component directory is /app/Java, /app/Hive, /app/Spark, /app/h dfs, then mount the /app directory into the container), and then all task scripts will be introduced to execute a common script to initialize environment variables at the beginning, set various Home and Path, and then you can use clients of various components in the container, such as Java, Hive, Spark, HDFS, etc.

2 airflow distributed container deployment solution

Inconsistent with official 2

  • The webserver and scheduler run as Docker containers. Only one instance is deployed on multiple nodes. Marathon ensures availability and marathon-lb does service discovery.
  • Workers use MesosExecutor:
    • The advantage of executing airflow tasks directly on mesos agent is that it can ensure that specific tasks can access cluster functions, such as Impala/flink. The disadvantage is that airflow needs to be deployed on the hosts of all mesos agent nodes.
    • Deploy the Docker container of airflow worker on mesos agent, and then execute the airflow task in the container. The advantage is that the deployment cost is zero. The disadvantage is that the Docker container only contains workers and cannot use the functions of external clusters. However, this shortcoming can be solved using the same method as LocalExecutor in the previous solution.
