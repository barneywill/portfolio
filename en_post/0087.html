Importing and Exporting Data Between Hive and MySQL

📅 October 10, 2019
📖 1 min read
👁️ 647 views

Hive and MySQL data mutually guide each other. The first thing that comes to mind is sqoop, and it can be configured with scheduling frameworks (such as oozie, etc.) to configure scheduled tasks. Another simpler way is through spark-SQL:

CREATE OR REPLACE TEMPORARY VIEW tmp_tbl_test
USING org.apache.spark.sql.jdbc OPTIONS (
url "jdbc:mysql://1.1.1.1:3306/db_test?useUnicode=true&characterEncoding=utf-8&tinyInt1isBit=false&zeroDateTimeBehavior=convertToNull",
dbtable "tbl_test",
user 'root',
password '123456');

Then you can read or write tmp_tbl_test in spark-SQL, which is equivalent to reading or writing MySQL directly.
If you only need to read, you don’t even need to pass the data from MySQL to Hive, but read MySQL directly;

 

If concurrent reading is required, you can add parameters

partitionColumn "id", 
lowerBound "10000", 
upperBound "20000", 
numPartitions "4"

Also note that if the query conditions in where are improperly set, it may result in a full table scan. This can be confirmed by explaining the query plan, such as common time types:

select * from test_table where create_time > '2019-01-01'

== Physical Plan ==
*(2) HashAggregate(keys=[], functions=[count(1)])
+- Exchange SinglePartition
   +- *(1) HashAggregate(keys=[], functions=[partial_count(1)])
      +- *(1) Project
         +- *(1) Filter (cast(create_time#2 as string) > 2019-01-01)
            +- *(1) Scan JDBCRelation(test_table) [numPartitions=1] [create_time#1643] PushedFilters: [], ReadSchema: struct<create_time:timestamp>
Time taken: 0.034 seconds, Fetched 1 row(s)

The above query plan will scan the entire test_table into spark and then filter create_time, instead of pushing the query conditions down into the scan. Obviously this is not the expected behavior. Modify the query conditions as

select * from test_table where create_time > date_sub(now(), 100)

then the problem can be solved; 

 

Also note:

1) tinyInt1isBit=false in the connection string. Since both spark-SQL and sqoop are based on JDBC to read MySQL, JDBC will default the field type tinyint of MySQL as java.SQL.Types.BIT, and what is read is not a digital int, but a Boolean value. If this default behavior is not required, you need to add tinyInt1isBit=false to the connection string;

2) zeroDateTimeBehavior=convertToNull in the connection string, if the MySQL date field value is 0000-00-00 00:00:00, an error will be reported when reading from spark:

java.sql.SQLException: Value '0000-00-00 00:00:00' can not be represented as java.sql.Timestamp

Set the zeroDateTimeBehavior property. When encountering a DATETIME value consisting entirely of 0s, the final valid value can be set to an exception (exception), an approximate value (round), or the value can be converted to null (convertToNull).
