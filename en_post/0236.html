1 Introduction

 

Docker is a platform for developers and sysadmins to develop, deploy, and run applications with containers. The use of Linux containers to deploy applications is called containerization. Containers are not new, but their use for easily deploying applications is.

Docker is a platform for developers and system administrators to develop, deploy, and run applications through containers; deploying applications through containers is also called containerization;

 

Containerization is increasingly popular because containers are:

  • Flexible: Even the most complex applications can be containerized.
  • Lightweight: Containers leverage and share the host kernel.
  • Interchangeable: You can deploy updates and upgrades on-the-fly.
  • Portable: You can build locally, deploy to the cloud, and run anywhere.
  • Scalable: You can increase and automatically distribute container replicas.
  • Stackable: You can stack services vertically and on-the-fly.

Containerization: flexible, lightweight, replaceable, portable, scalable, and stackable;

 

An image is an executable package that contains all dependencies. An instance running an image is called a container. One or more containers running the same image on one (or more) machines are called services; containerized deployment on multiple machines is called a swarm;

1 Container、Image

A container is launched by running an image. An image is an executable package that includes everything needed to run an application--the code, a runtime, libraries, environment variables, and configuration files.

When running an image, a container will be started. An image is an executable package that contains all the information required for running (including code, libraries, environment variables, configuration files, etc.);

A container is a runtime instance of an image--what the image becomes in memory when executed (that is, an image with state, or a user process). You can see a list of your running containers with the command, docker ps, just as you would in Linux.

A container is a runtime instance of an image. You can view all running containers through the Docker ps command;

A container runs natively on Linux and shares the kernel of the host machine with other containers. It runs a discrete process, taking no more memory than any other executable, making it lightweight.

A container runs as a native process on Linux and does not occupy other memory, so it is very lightweight;

2 Dockerfile

Dockerfile defines what goes on in the environment inside your container. Access to resources like networking interfaces and disk drives is virtualized inside this environment, which is isolated from the rest of your system, so you need to map ports to the outside world, and be specific about what files you want to “copy in” to that environment. However, after doing that, you can expect that the build of your app defined in this Dockerfile behaves exactly the same wherever it runs.

The dockerfile defines a running environment inside the container. In this environment, access to external resources (such as networks, interfaces, and disks) are virtualized to achieve isolation from external systems, so you need to do port mapping, specify which files need to be accessible in the environment, etc.;

3 Registry

A registry is a collection of repositories, and a repository is a collection of images—sort of like a GitHub repository, except the code is already built. An account on a registry can create many repositories. The docker CLI uses Docker’s public registry by default.

A registry is a collection of multiple warehouses, and a warehouse is a collection of multiple images; the Docker command line uses the Docker public registry by default;

4 Service

Services are really just “containers in production.” A service only runs one image, but it codifies the way that image runs—what ports it should use, how many replicas of the container should run so the service has the capacity it needs, and so on. Scaling a service changes the number of container instances running that piece of software, assigning more computing resources to the service in the process.

Luckily it’s very easy to define, run, and scale services with the Docker platform -- just write a docker-compose.yml file.

Service only runs one image. Service is a collection of multiple containers running the same image. Service can configure ports, resources, number of containers, etc. Service is defined through Docker-compose.yml;

A single container running in a service is called a task. Tasks are given unique IDs that numerically increment, up to the number of replicas you defined in docker-compose.yml.

A continer in a service is also called a task, and each task has a unique self-increasing ID;

5 Swarm

A swarm is a group of machines that are running Docker and joined into a cluster. After that has happened, you continue to run the Docker commands you’re used to, but now they are executed on a cluster by a swarm manager. The machines in a swarm can be physical or virtual. After joining a swarm, they are referred to as nodes.

Swarm managers are the only machines in a swarm that can execute your commands, or authorize other machines to join the swarm as workers. Workers are just there to provide capacity and do not have the authority to tell any other machine what it can and cannot do.

A swarm is a group of machines running Docker; a swarm cluster is divided into swarm managers and workers;

Among them: -p = --publish (port mapping), -d = --detach (background running)

Run the app, mapping your machine’s port 80 to the container’s published port 80 using - p (--publish)

Note: After port mapping, you can access the corresponding port directly through localhost:port on Linux, but not on Windows, because Docker is implemented differently on different platforms. On Windows, you need to first access it through

$ docker-machine ip default

Find the virtual machine IP of virtualbox, usually 192.168.99.100, and then access 192.168.99.100:port

The reason you’re having this, is because on Linux, the docker daemon (and your containers) run on the Linux machine itself, so “localhost” is also the host that the container is running on, and the ports are mapped to.
On Windows (and OS X), the docker daemon, and your containers cannot run natively, so only the docker client is running on your Windows machine, but the daemon (and your containers) run in a VirtualBox Virtual Machine, that runs Linux.

6) Execute commands within the container, such as reload Nginx

# docker exec d727449d221f service nginx reload

7) Log in to the running container ($container_id can be seen from Docker container ls). After logging in, you can perform operations such as reload.

$ docker exec - it $container_id bash

8) Stop running containers

$ docker container stop <Container NAME or ID>
$ docker stop <Container NAME or ID>

9) Start the container

$ docker start <Container NAME or ID>

10) View container logs

$ docker logs <Container NAME or ID>

The premise is that the container is still running. If the container fails to start, there are two ways to view the log: 1) Mount the log directory; 2) Use export as follows:

11) Export container file system

$ docker export $container_id - o save.zip

12) Delete container

$ docker rm <Container NAME or ID>

13) View all current images

$ docker images

14) Delete image

$ docker rmi $image_id

15) Copy files between the container and the host

$ docker cp $container_id:/container/path/to/file.txt /host/path/dir/

16) Limit the memory used by containers

$ docker run --memory 300M --memory-swap=1G nginx

--memory=-m limits the maximum physical memory used by the container, --memory-swap limits the maximum physical memory + swap used by the container

17) View container ip

$ docker inspect - f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' $container_id_or_name

6 Swarm command

swarm cluster

1) swarm manager starts and stops

$ docker swarm init
$ docker swarm leave --force

2) worker starting and stopping

$ docker swarm join
$ docker swarm leave

run docker swarm init to enable swarm mode and make your current machine a swarm manager, then run docker swarm join on other machines to have them join the swarm as workers.

Install swarm cluster on vm

1) Create vm

$ docker-machine create --driver virtualbox myvm1
$ docker-machine create --driver virtualbox myvm2
$ docker-machine ls
$ docker-machine start <machine-name>
$ docker-machine ssh myvm1
$ docker-machine env myvm1

You need to install VirtualBox first

# yum install opus
# yum install libvpx
# wget http://download.virtualbox.org/virtualbox/rpm/rhel/7/x86_64/VirtualBox-5.2-5.2.8_121009_el7-1.x86_64.rpm
# rpm - ivh VirtualBox-5.2-5.2.8_121009_el7-1.x86_64.rpm
# usermod - G vboxusers $user

Note that version 5 must be installed (the latest is 6), otherwise an error will be reported:

Error with pre-create check: "We support Virtualbox starting with version 5. Your VirtualBox install is \"WARNING: The vboxdrv kernel module is not loaded. Either there is no module\\n available for the current kernel (3.10.0-693.el7.x86_64) or it failed to\\n load. Please recompile the kernel module and install it by\\n\\n sudo /sbin/vboxconfig\\n\\n You will not be able to start VMs until this problem is fixed.\\n6.0.4r128413\". Please upgrade at https://www.virtualbox.org"

2) Start the swarm cluster on the vm

$ docker-machine ssh myvm1 "docker swarm init --advertise-addr <myvm1 ip>"
$ docker-machine ssh myvm2 "docker swarm join --token <token> <ip>:2377"

3) Deploy the application in the swarm cluster on the vm

$ docker stack deploy - c docker-compose.yml getstartedlab
$ docker stack ps getstartedlab
$ docker stack rm getstartedlab

4) Stop the swarm cluster on the vm

$ docker-machine ssh myvm2 "docker swarm leave"
$ docker-machine ssh myvm1 "docker swarm leave --force"
