1.4 Why do Kafka processes exit at different times?

Each Kafka partition has a leader. Only the leader will append the message, so only the leader can execute the above code and exit the process.

 

The leader will determine whether roll is needed when accepting the message. When the segment size exceeds the limit or the segment existence time exceeds the limit, it will perform roll. When the leader executes roll, it will report an error and exit;

 

So at the beginning, 135 served as the leader, and then executed roll and exited at 11:02:35 on the 11th:

Then 134 takes over as leader, and then executes roll at 16:45:41 on the 13th and exits with an error:

In the end, only 136 was left to take over as leader, and then executed roll at 19:10:35 on the 13th and exited with an error:

Three problem positioning

There are several possibilities for the Partition directory to be deleted, one is deleted by the operating system, one is deleted manually, and the other is deleted by Kafka itself;

1 operating system removal

The /tmp directory is a temporary directory, and the operating system will be responsible for deleting expired files.

 

 

Checking the cron log found that the time when 134-136 executed tmpwatch that day was around 3 a.m., and it was only executed once.

Oct 11 03:28:02 hz1-13-134 run-parts(/etc/cron.daily)[24593]: starting tmpwatch

Oct 11 03:28:02 hz1-13-134 run-parts(/etc/cron.daily)[24829]: finished tmpwatch

 

Ps：

tmpwatch recursively removes files which haven't been accessed for a given time. Normally, it's used to clean up directories which are used for temporary holding space such as /tmp.

It does not follow symbolic links in the directories it's cleaning (even if a symbolic link is given as its argument), will not switch filesystems, skipslost+found directories owned by the root user, and only removes empty directories, regular files, and symbolic links.

By default, tmpwatch dates files by their atime (access time), not their mtime (modification time). 

 

 

2 Manually deleted

 

The Kafka log directory belongs to root, and only root has write permissions, so if it is deleted manually, it can only be deleted by root itself, which is unlikely.

 

Ps: Manually deleting the partition directory can easily reproduce server errors;

 

3 Kafka deletes itself

Looking at the Kafka code, we found that there is indeed a method to delete a partition, located in Kafka.cluster.Partition:

 

The deleteLog method of LogManager is as follows:

 

The delete method of Log is as follows:

 

The method will iteratively delete all segments, then clear the segment variables, and finally delete the partition directory;

 

There are two points to consider here:

  1. The problem occurs because Kafka thinks that the partition exists but in fact the partition has been deleted for some reason, so an error is reported. If the above deleteLog method is called to delete the partition, it means that Kafka must know that the partition has been deleted (the segments variable is cleared, and segments.lastEntry() will definitely not be available when rolling), so there will be no problem;
  2. To execute roll, the current broker needs to be the leader of the partition, but the above deleteLog method is called by ReplicaManager.stopReplica. If stopReplica is called, it means that the current broker is no longer the replica of the partition, let alone the leader;

The above two points can prove that Kafka did not delete the partition directory by itself;

 

Four causes of the problem

1 background

1.1 Kafka’s retention check will call the Kafka.log.Log.deleteOldSegment method:

 

It can be found that if there is no new message, the last segment will always be empty. At this time, the segment will not be deleted or rolled. This segment will remain intact;

1) If the segment is empty during the retention check, roll will not be executed. Even if the partition directory is empty, no error will be reported, soIt is not possible to directly infer the time when the directory was deleted based on the error time.；

2) If a segment is empty for a long time, it may meet the deletion conditions of tmpwatch, that is, it has not been accessed for more than 10 days. If the segment file is deleted, the partition directory will become an empty directory and will also be deleted;

 

1.2 Kafka will call the Kafka.log.Log.append method when receiving a message, and the append method will call the maybeRoll method:

 

It can be found that when the segment is empty, that is, segment.size=0, even if the segment creation time exceeds the limit, roll will not be performed when receiving the first message, but after receiving the first message, segment.size>0, then if the second message is received, roll will be performed;

3. The actual problem occurrence process

3.1 135 server

1）2014-10-01 03:44Previously, Kafka performed a retention check on the partition cacheClear-onlineConfirm-1, deleted the old segment and created a new empty segment;

2) No new message arrives in partition cacheClear-onlineConfirm-1 from 2014-10-01 03:44 to 2014-10-11 03:44, so this partition always has only one empty segment;

3）2014-10-11 03:44 anacron is executed and tmpwatch is called to clean up the /tmp directory. The full path of partition cacheClear-onlineConfirm-1 is /tmp/Kafka-logs/ cacheClear-onlineConfirm-1. tmpwatch finds that the partition directory was last accessed 10 days ago and deletes it;

4) Kafka has been performing retention checks between 2014-10-11 03:44 and 11:00:03, but because the segment variable in the memory is an empty segment, roll is not executed and no error is reported;

5) Between 2014-10-11 10:59:38 and 11:00:38, the first message arrived in partition cacheClear-onlineConfirm-1;

6）2014-10-11 11:00:38, Kafka performs retention check. At this time, the segment is not empty, enters roll, and then starts to report errors (ERROR);

7）2014-10-11 11:02:35, the second message reaches the partition cacheClear-onlineConfirm-1. At this time, Kafka rolls before append, reports an error (FATAL), and the Kafka process exits;

3.2 134 server

1) After server 135 hangs up, server 134 takes over the partition cacheClear-onlineConfirm-1 as the leader;

2）2014-10-13 16:45:41, 134 The server receives the first message, executes roll, reports an error (FATAL), and the process exits;

3.3 136 server

1) After server 134 hangs up, server 136 takes over the partition cacheClear-onlineConfirm-1 as the leader;

2）2014-10-13 19:10:35, 136 The server receives the first message, executes roll, reports an error (FATAL), and the process exits;

 

Five Summary of Problems

1) Using the default Kafka log directory /tmp/Kafka-logs is a hidden danger. You can first add /tmp/Kafka-logs to the directory exclusion list of /etc/cron.daily/tmpwatch;

2) In addition, you can sort out Kafka's logs, especially ERROR and FATAL, and monitor the logs to find problems in time;
