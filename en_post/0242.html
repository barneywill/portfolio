1 Introduction

Keepalived is a routing software written in C. The main goal of this project is to provide simple and robust facilities for loadbalancing and high-availability to Linux system and Linux based infrastructures. Loadbalancing framework relies on well-known and widely used Linux Virtual Server (IPVS) kernel module providing Layer4 loadbalancing. Keepalived implements a set of checkers to dynamically and adaptively maintain and manage loadbalanced server pool according their health. On the other hand high-availability is achieved by VRRP protocol. VRRP is a fundamental brick for router failover. In addition, Keepalived implements a set of hooks to the VRRP finite state machine providing low-level and high-speed protocol interactions. In order to offer fastest network failure detection, Keepalived implements BFD protocol. VRRP state transition can take into account BFD hint to drive fast state transition. Keepalived frameworks can be used independently or all together to provide resilient infrastructures.

keepalived is a routing software written in C that uses vrrp protocol (Virtual Router Redundancy Protocol) and arp protocol (Address Resolution Protocol) to achieve simple and robust load balancing and high availability;

 

VRRP organizes a group of routers on the LAN (including a Master (active router) and several Backup routers) into a virtual router, which is called a backup group. This virtual router has its own IP address 10.100.10.1 (this IP address can be the same as the interface address of a router in the backup group, and the same one is called the IP owner). The routers in the backup group also have their own IP addresses (for example, the Master's IP address is 10.100.10.2, and the Backup's IP address is 10.100.10.3). Hosts in the LAN only know the IP address of this virtual router, 10.100.10.1, but do not know the specific IP address of the Master router, 10.100.10.2, and the IP address of the Backup router, 10.100.10.3. They set their default route next hop address to the virtual router's IP address of 10.100.10.1.

 

principle

The master and slave nodes send vrrp packets through broadcast or multicast, and then elect the master based on priority.

14:20:21.521870 IP 192.168.0.1 > 192.168.0.2: VRRPv2, Advertisement, vrid 99, prio 100, authtype simple, intvl 1s, length 20

Once the master does not send out vrrp packets in time within a certain period of time, other standbys will send vrrp packets and then elect the master based on priority;

The master will send the arp package,

Jan 28 19:04:26 cdp-test-server-05 Keepalived_vrrp[27675]: VRRP_Instance(VI_1) Sending/queueing gratuitous ARPs on eth0 for 192.168.0.3
Jan 28 19:04:26 cdp-test-server-05 Keepalived_vrrp[27675]: Sending gratuitous ARP on eth0 for 192.168.0.3

Note that this is the gratuitous ARP of the virtual ip (vip).

Let’s first look at ARP (Address Resolution Protocol, Address Resolution Protocol), which converts IP addresses into MAC addresses.

The process of ARP: Send an ARP request on Host A with the content of who has [IP_B], tell [IP_A]. The packet carries the IP address of Host B, as well as the IP and MAC of Host A. All hosts that receive the broadcast packet will check whether the requested IP address is their own. If so, they will send an ARP reply (unicast, from B to A) with the content [IP_B] is at [MAC_B]. The packet carries the MAC and IP addresses of hosts A and B.

# arping 192.168.0.1

In the scenario just now, if Host A sends a request with the content "who has [IP_A], tell [IP_A]", then this is a gratuitous ARP. Why does it request its own IP? Because: normal ARP requests information from other hosts, while gratuitous ARP actively broadcasts its own information to other hosts, so gratuitous ARP does not expect a response;

All hosts or switches that receive broadcast packets after sending gratuitous ARP can view the VIP and mac (master mac) mapping through the command:

# arp -a

In this way, other hosts can access the master through vip or bind manually through arp.

# arp -s 192.168.0.3 00-02-b3-3c-16-95

In addition, you can set vrrp_garp_master_refresh to let the master send gratuitous ARP packets regularly;

If you are in a cloud host environment, you do not need to consider keepingalived, because multicast and arp of the vrrp protocol are usually prohibited on the cloud. You can consider directly using the virtual IP service of the cloud platform;

2. Installation

# yum install keepalived

Master node configuration

# vi /etc/keepalived/keepalived.conf

vrrp_instance VI_1 {

    state MASTER

    interface eth0

    unicast_src_ip 192.168.0.1

    unicast_peer {

        192.168.0.2

    }

    virtual_router_id 51

    priority 100

    advert_int 1

    authentication {

        auth_type PASS

        auth_pass 1111

    }

    virtual_ipaddress {

        192.168.0.3

    }

}

 

virtual_server 192.168.0.3 81 {

    delay_loop 6

    lb_algo rr

    lb_kind DR

    nat_mask 255.255.255.0

    persistence_timeout 50

    protocol TCP

    #sorry_server 127.0.0.1 80

    real_server 192.168.0.1 80 {

        weight 1

    }

    real_server 192.168.0.2 80 {

        weight 1

    }

}

The unicast (unicast_src_ip, unicast_peer) method is used here, because multicast cannot be used in many environments. If you want to use multicast, just remove the unicast parameters;

If real_server and keealived are deployed on the same machine, there is no need to configure virtual_server;

Comment out

    #vrrp_strict

Otherwise, a drop rule will be generated in iptables;
