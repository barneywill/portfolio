An error was reported in step 6: Java.lang.NoSuchFieldError: HIVE_MOVE_FILES_THREAD_COUNT

 

This problem is usually considered to be a lack of configuration in Hive-site.XML

  <property>

    <name>hive.mv.files.thread</name>

    <value>15</value>

  </property>

But looking at the code, you will find that spark2.1.1 depends on hive1.2.1, which is not available in hive1.2.1.hive.mv.files.threadThis configuration, this configuration only started to appear in hive2, and the type of error reportedorg.apache.hadoop.hive.ql.metadata.HiveThe relevant codes in hive1.2.1 and hive2 are completely different. The specific points are as follows:

 

The code in hive1.2.1 is: (trashFilesUnderDirThe method is FileUtilsclass）

            if (FileUtils.isSubDir(oldPath, destf, fs2)) {

              FileUtils.trashFilesUnderDir(fs2, oldPath, conf);

            }

The code in hive2 is:(trashFilesUnderDirThe method is Hiveclass）

  private boolean trashFilesUnderDir(final FileSystem fs, Path f, final Configuration conf)

      throws IOException {

    FileStatus[] statuses = fs.listStatus(f, FileUtils.HIDDEN_FILES_PATH_FILTER);

    boolean result = true;

    final List<Future<Boolean>> futures = new LinkedList<>();

    final ExecutorService pool = conf.getInt(ConfVars.HIVE_MOVE_FILES_THREAD_COUNT.varname, 25) > 0 ?

        Executors.newFixedThreadPool(conf.getInt(ConfVars.HIVE_MOVE_FILES_THREAD_COUNT.varname, 25),

        new ThreadFactoryBuilder().setDaemon(true).setNameFormat("Delete-Thread-%d").build()) : null;

 

Therefore, the error reported in step 6 should be the code of hive2, so the guessed problem may be:

1) Due to jar package contamination, there are both hive1 and hive2 jars in the classpath when starting the JVM. Sometimes the hive1 jar is used to load classes (it can run normally), and sometimes the hive2 jar is used (an error will be reported);

2) There are differences in the configuration of the cluster server environment. Some servers do not have the hive2 jar in the classpath (can run normally), and some servers have the hive2 jar in the classpath (an error may be reported);

 

Comparing the environment configuration and startup commands of the normal and error-reported servers, we found that they were the same, and no hive2 jar was found.

By adding -verbose:class when starting the task, we found that Hive classes are loaded from the jar of Hive1.2.1 under normal and error conditions.

[Loaded org.apache.hadoop.hive.ql.metadata.Hive from file:/export/Data/tmp/hadoop-tmp/nm-local-dir/filecache/98/hive-exec-1.2.1.spark2.jar]

The above two speculations are denied;

 

After analyzing the submit task command, we found that it is usedspark.yarn.jars, avoid uploading Spark jars every time, these jars will be cached in filecacheyarn.nodemanager.local-dirsDown,

The decompilation is normal and the error message is in the filecache on the server.hive-exec-1.2.1.spark2.jarFinally found the problem,

The Hive class code on a normal server is:

    if (FileUtils.isSubDir(oldPath, destf, fs2))

        FileUtils.trashFilesUnderDir(fs2, oldPath, conf);

The Hive class code on the error reporting server is:

    private static boolean trashFilesUnderDir(final FileSystem fs, Path f, final Configuration conf) throws IOException {

        FileStatus[] statuses = fs.listStatus(f, FileUtils.HIDDEN_FILES_PATH_FILTER);

        boolean result = true;

        List<Future<Boolean>> futures = new LinkedList();

        ExecutorService pool = conf.getInt(ConfVars.HIVE_MOVE_FILES_THREAD_COUNT.varname, 25) > 0 ? Executors.newFixedThreadPool(conf.getInt(ConfVars.HIVE_MOVE_FILES_THREAD_COUNT.varname, 25), (new ThreadFactoryBuilder()).setDaemon(true).setNameFormat("Delete-Thread-%d").build()) : null;

The Hive class on the error reporting server is usedConfVars.HIVE_MOVE_FILES_THREAD_COUNT, but this attribute does not exist in ConfVars in Hive-common-1.2.1.jar, so an error is reportedjava.lang.NoSuchFieldError，

So the problem should be on HDFShive-exec-1.2.1.spark2.jarIt was correct at first, and then all nodemanagers downloaded it locally as filecache. Later, the jar was corrected (using hive2 to compile Spark), and then the newly added nodemanager downloaded the problematic jar as filecache. The result was that some servers executed normally, and some servers reported errors;

 

There are two configurations for filecache cleaning in YARN

yarn.nodemanager.localizer.cache.cleanup.interval-ms：600000  Interval in between cache cleanups.

yarn.nodemanager.localizer.cache.target-size-mb：10240    Target size of localizer cache in MB, per local directory.

Every cleanup.interval-ms will check whether the local filecache size exceeds target-size-mb. If it exceeds, it will be cleaned. If it does not exceed, the filecache will be used.
