public Logger getLogger(String name, LoggerFactory factory) {
    CategoryKey key = new CategoryKey(name);
    synchronized(this.ht) {
        Object o = this.ht.get(key);
        Logger logger;
        if (o == null) {
            logger = factory.makeNewLoggerInstance(name);
            logger.setHierarchy(this);
            this.ht.put(key, logger);
            this.updateParents(logger);
            return logger;
        } else if (o instanceof Logger) {
            return (Logger)o;
        } else if (o instanceof ProvisionNode) {
            logger = factory.makeNewLoggerInstance(name);
            logger.setHierarchy(this);
            this.ht.put(key, logger);
            this.updateChildren((ProvisionNode)o, logger);
            this.updateParents(logger);
            return logger;
        } else {
            return null;
        }
    }
}

Code analysis

  • There is a Hashtable type variable ht in the Hierarchy object, which is used to save the logger. Whenever getLogger is called, it first tries to get the logger from ht according to the name. If it cannot find it, a new logger will be created and placed in ht.

private void closeLogger() {
  if (this.jobAppender != null) {
    removeAppender(this.jobAppender);
  }
  if (this.kafkaAppender.isPresent()) {
    removeAppender(this.kafkaAppender);
  }
}

Code analysis

  • JobRunner in azkaban has a createLogger method. The loggerName here is composed of: current timestamp + executionId + jobId, and closeLogger does not release the logger from log4j.
  • The above code will cause a problem. The loggerName of createLogger is different every time. As the server runs, the number of loggers will continue to increase. That is, the ht in the Hierarchy will continue to expand until the memory is full. This is a typical memory leak problem.
